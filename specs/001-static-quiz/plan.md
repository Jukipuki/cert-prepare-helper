# Implementation Plan: Static Practice Quiz — Zen and Exam Modes

**Branch**: `001-static-quiz` | **Date**: 2026-08-10 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-static-quiz/spec.md`

## Summary

A client-side quiz over the 53-question CCDV-F practice set, offering two modes: zen (untimed,
explanation after each question, backward navigation) and exam (120-minute countdown, all disclosure
deferred to the end, free navigation via a question grid). Nothing is stored, nothing is transmitted,
no account is involved.

The technical approach is shaped by three constraints that fall out of the spec and the constitution:

1. **Content is bundled, not fetched.** The question set is generated from the canonical seed
   migration by a committed export step and shipped with the application, so a session runs with no
   data service reachable (FR-005) and no credential exists to leak.
2. **The content origin sits behind one asynchronous boundary.** A single `QuestionSource` port is
   the only thing that knows where questions come from, so replacing the bundle with Supabase later
   changes one module and no behaviour (FR-006).
3. **Session logic is pure and framework-free.** Grading, scoring, deadline arithmetic and the
   session state machine are plain functions in `src/domain/`, unit-tested directly. React renders
   them; it does not own them.

## Technical Context

**Language/Version**: TypeScript 5.x, strict mode, `noUncheckedIndexedAccess` enabled

**Runtime**: Node ≥ 22 for build and tooling (development machine is on 26.5.0)

**Primary Dependencies**: Next.js (App Router) + React, Tailwind CSS, Zod for content validation.
Exact versions pinned at scaffold time — see research.md R1, which flags version confirmation as a
setup step rather than an assumption.

**Storage**: None at runtime. Question content is a build-time artifact generated from
`sql/002_seed_ccdv_f_questions.sql`. No database, no `localStorage`, no cookies, no server state.

**Testing**: Vitest (unit + component, with React Testing Library), Playwright (end-to-end,
including keyboard-only traversal, fake-clock timer expiry, and a network assertion for SC-015)

**Target Platform**: Current desktop and mobile browsers; deployed on Vercel

**Project Type**: Web application — single Next.js app, no backend of its own in this release

**Performance Goals**: Zen feedback < 100 ms (SC-003); question-to-question transition with no
waiting state (SC-004); LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1 at p75 (Principle IV)

**Constraints**: Initial client JS ≤ 200 KB gzipped (Principle IV) — the generated content is 20 KB
gzipped on its own, so it is loaded as a separate chunk rather than inlined into the entry bundle.
Countdown accurate to within 2 s over 120 minutes including backgrounding (SC-009). Zero
third-party requests (SC-015).

**Scale/Scope**: 53 questions, 8 domains, one exam, one concurrent user per tab. Roughly 6 screens:
mode choice, zen question, exam question, exam grid, results summary, session review.

**Structure Decision**: The application lives in `web/` rather than at the repository root. The
repository is deliberately multi-artifact — the Cowork kit, the prompts and the SQL are published
deliverables in their own right, and burying them next to `node_modules/`, `.next/` and a root
`package.json` would obscure that. The cost is a single Vercel setting (Root Directory = `web`) and
a `cd`; the benefit is that the repo's other contents stay legible. Within `web/`, `src/domain/`
holds framework-free logic so the rules that matter — grading, scoring, deadlines, state
transitions — are testable without rendering anything.
